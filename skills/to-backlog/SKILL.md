# Project Backlog

Maintain `docs/backlog.md` as the source of truth for concrete work another developer can pick up. The skill is independent: it reads only its own `references/backlog-template.md` and invokes only its own `scripts/`; `docs/overview.md` and `docs/recap.md` are optional, read-only context.

## Boundaries

- Create `docs/` and write only `docs/backlog.md`; preserve unrelated files and documentation.
- Read the local template before creating or updating the backlog. Use its five status sections and concise item fields.
- Preserve every existing ID, including `Done` items and their exact completion records. Never renumber, recycle, delete, or silently reopen an ID.
- Use exactly these statuses: `Todo`, `In Progress`, `Blocked`, `Needs Review`, `Done`.
- Use exactly these priorities: `High`, `Medium`, `Low`.
- Do not modify `docs/overview.md`, `docs/recap.md`, source files, or Git state.

## Conservative workflow

1. Establish the repository root and inspect `docs/` without assuming it exists. From the target repository root, run `bash <installed-to-backlog>/scripts/working-tree.sh "$PWD"` to collect branch, `HEAD`, bounded working-tree status, and separately labeled staged/unstaged changed-file lists and diffstats. These are read-only summaries, not full patches; inspect specific paths locally when their meaning matters. If the helper exits nonzero, stop and investigate rather than inventing Git facts; `GIT=none` is a valid result. Read existing `docs/backlog.md` if present, and consult `docs/overview.md` or `docs/recap.md` only as optional evidence.
2. Discover open GitHub issues and local plan/spec work before reconciliation. Run `bash <installed-to-backlog>/scripts/list-open-issues.sh "$PWD"` and `bash <installed-to-backlog>/scripts/find-open-plans.sh "$PWD"` as separate read-only helpers. The GitHub helper emits one JSON object per open issue (including `wontfix` issues) and excludes pull requests and closed issues. The local helper emits `PLAN_FILE=<shell-escaped-relative-path>` records for eligible documents under `docs/plans`, `docs/specs`, or `.scratch/**/issues`. Decode each path without evaluating its content. If local plan discovery fails, stop before drafting or writing: local coverage is unknown. If issue discovery fails, discard all stdout from that helper, mark GitHub coverage incomplete, and continue with local discovery and TODO discovery; disclose the gap in the result and never claim a complete issue scan. Missing `gh` is optional, not a blocker to local intake.
3. Run `bash <installed-to-backlog>/scripts/find-todos.sh "$PWD"` to collect bounded TODO/FIXME/HACK/XXX/WIP leads. If it exits nonzero, stop and investigate; no matches is not a failure. If the scanner reports safe leads omitted by its per-file 100 or global 120 limits, follow up before claiming discovery complete: run `bash <installed-to-backlog>/scripts/find-todos.sh "$PWD" "relative/path with spaces" 102` with the reported file and first omitted line, repeat at later reported lines, and narrow other affected files or repository areas if the global limit obscures them. Never print a sensitive TODO line as a workaround; disclose any coverage gaps that cannot be resolved. Combine safe leads with the current request, concrete implementation gaps, Git state, optional project-memory context, open issues, and eligible local plans/specs as evidence; do not treat scan output as requirements by itself.
4. Reconcile sources conservatively. Create one item per open issue and one per eligible plan/spec document, grouping that document's unfinished checklist tasks under one item. A document containing unrelated outcomes belongs in `Needs Review`; do not split it automatically. Combine an issue and document only when the document explicitly cross-references the issue. Put issue URLs and local document paths in `Related`. Map every open issue, including `wontfix`, to `Todo`; closed issues and completed local sources are not new work. Recognize only exact-case local statuses `Todo`, `In Progress`, `Blocked`, `Needs Review`, and `Done`. Unknown explicit statuses become `Needs Review`, with the original value preserved in `Context`. Unfinished work without a status defaults to `Todo`; conflicting `Done` status and unchecked tasks require `Needs Review`. For an existing non-`Done` item whose source closes or completes, use `Needs Review` unless direct completion evidence supports `Done`; preserve existing `Done` records exactly. Update source-derived context only when its provenance is clear. If provenance is uncertain or source changes materially alter outcome, scope, or remaining tasks, preserve the existing text and move the item to `Needs Review`. Retain human-curated tasks/status and all stable IDs.
5. For each candidate, document why it matters and what finite next actions are supported. Do not infer acceptance criteria, scope, urgency, dependencies, or a blocker that the repository does not support. Put unresolved uncertainty in `Needs Review` and state what evidence is missing. Keep `Related`, `Files`, `Depends on`, and `Blocked by` only if useful; omit irrelevant fields rather than filling them with `None`.
6. Reconcile existing items conservatively. Update status, priority, tasks, dependencies, or blocker fields only when current repository evidence supports the change. Preserve completed items and all their recorded details intact; only mark `Done` with direct completion evidence (for example, a verified diff, commit, or command result). Do not treat an uncommitted change as completed work. Unfinished items need no completion fields.
7. Allocate new IDs by scanning all existing IDs (including `Done`) and available Git history. Use the next unused `BL-###` number; never reuse a historical ID, renumber items, or fill gaps. If history is unavailable, preserve every visible ID and choose a new number above the highest visible ID.
8. Assign `High`, `Medium`, or `Low` from evidence-backed impact, urgency, or blocking effect. Never infer `High` or `Medium`; when no severity evidence exists, use conservative `Low` and state that the priority basis is unknown or needs verification. Add `Blocked by` only for a demonstrated blocker and `Depends on` only for a real prerequisite, never as empty boilerplate.
9. **Guard the owned file before writing.** For an existing `docs/backlog.md`, inspect its hidden `skill-state` HTML comment, which contains an `output_sha256: <64 lowercase hex characters>` line. Validate by removing only the entire `output_sha256: <value>` line, preserving its line ending, the surrounding comment delimiters, and every other byte; calculate SHA-256 over the resulting exact UTF-8 bytes. A matching value permits updating even if Git reports the file dirty. If the field exists but is malformed or does not match, stop and ask how to preserve or merge the edits; do not write. If the field is absent, adopt the legacy document only in a Git repository when `git ls-files --error-unmatch -- docs/backlog.md` confirms it is tracked and `git status --short -- docs/backlog.md` is clean. If `docs/backlog.md` is untracked or modified, stop; do not overwrite it. Never infer ownership from formatting or content alone.
10. Draft the complete result in a private temporary directory outside the target repository (create it with `mktemp -d`, clean it on exit) and keep a byte-for-byte copy of the guarded previous document there when updating. Retain all five sections even when one is empty. The template's `Item format` section is authoring guidance and must not be copied into the generated backlog. Include exactly one hidden comment of the form `<!-- skill-state\noutput_sha256: <64 lowercase hex characters>\n-->`. Calculate the SHA-256 over the candidate's exact UTF-8 bytes with only the `output_sha256: <value>` line omitted; preserve its line ending and the surrounding HTML comment delimiters when hashing. Do not create another output in the target repository.
11. Before publication, run `bash <installed-to-backlog>/scripts/validate-backlog.sh <candidate> <previous-copy>` for updates, or `bash <installed-to-backlog>/scripts/validate-backlog.sh <candidate>` on creation. A signed, clean-looking candidate can still be rejected for changing or dropping a previous ID or completion record. Correct rejected candidates outside the repository; never publish one. After validation, publish only `docs/backlog.md` and validate that exact file with the same previous-copy argument on updates. The validator checks required core fields, status/priority consistency, unique and preserved IDs, direct `Done` evidence, unchanged previously completed records, and the fingerprint without modifying the document. Separately verify evidence, credential safety, and all claims, including source coverage. Do not publish a partial candidate after any failed guard or validation.
12. Report the result briefly: say what changed or why no item changed, list assigned IDs and priorities, name unresolved evidence gaps including incomplete GitHub issue coverage, and confirm validation. Do not claim GitHub discovery was complete after any helper failure.

## Evidence and update rules
- Git metadata and staged/unstaged diff summaries are context, not automatically backlog work or evidence of completion. An uncommitted change, branch divergence, or failed command becomes an item only when the repository provides a concrete unfinished outcome; otherwise mention it in `Context` or omit it. Keep staged and unstaged changes distinct, and never mark an item `Done` merely because local changes appear to implement it.
- A `TODO`/`FIXME` becomes an item only when it represents pick-up-worthy work. “Remove debug log”, formatting, vague reminders, and one-line cleanup remain out of the backlog unless the request supplies evidence of meaningful risk or scope.
- Never manufacture product requirements, tests, deadlines, priorities, dependencies, related files, or completion claims. Use `Unknown` or `Needs verification` in `Context` when evidence is missing.

## Completion check

Before finishing, confirm: output is exactly `docs/backlog.md`; `docs/` exists; old IDs and `Done` records remain; scan omissions were followed up or explicitly labeled as an evidence gap; only meaningful work was promoted; uncommitted changes were not called complete; statuses and priorities use the allowed values; blockers and dependencies are explicit; and all claims can be traced to repository evidence.
