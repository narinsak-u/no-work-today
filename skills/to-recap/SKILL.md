# Incremental Project Recap

Maintain an evidence-based, append-only `docs/recap.md`. Use only this skill's `scripts/` and `references/recap-template.md`; it must work when installed alone. Scripts collect and validate facts but never interpret commits, edit the repository, or advance a checkpoint. Only the agent writes the recap. Create `docs/` if needed; never edit another generated document.

## Ownership and history guards

1. Find the Git root, non-empty branch, full `HEAD`, and working-tree status. Stop for a non-Git directory, empty repository, detached HEAD, or shallow history: its boundary cannot be verified. Do not invent a checkpoint. Inspect optional `docs/overview.md` and `docs/backlog.md` only as context, and verify their claims against Git evidence.
2. Read the entire existing recap before updating. If it has a fingerprint, run `bash scripts/validate-checkpoint.sh "$root" "$root/docs/recap.md" "$head"`. A mismatch, malformed or duplicate field, missing/rebased/non-ancestor commit, or branch change is a stop: preserve all entries and state and ask for direction; inspect refs/graph when helpful, but never guess continuity. Fingerprint checks apply even if the recap is staged or unstaged. The SHA-256 fingerprint is the lowercase digest of the exact UTF-8 document bytes after deleting ONLY its complete `output_sha256: ...` line and line terminator. Keep all other bytes, delimiters, line endings, and whitespace exactly as they were. Require one correct field immediately before the closing `-->` of the final `recap-state` block. For updates compute it over the completed fingerprint-free draft and insert that line immediately before `-->`.
3. For an existing recap without a fingerprint (legacy), adopt it ONLY if `git ls-files --error-unmatch docs/recap.md` succeeds and `git status --short -- docs/recap.md` is empty. Verify its `Current Point` branch (`HEAD ... on <branch>`) exactly matches the current branch, its last checkpoint is an unambiguous ancestor of `HEAD`, and all existing entries remain intact. Otherwise ask; never silently treat it as a new recap or ignore unowned edits. Add a fingerprint and branch on the first safe complete update.
4. If the previous state has both `history_head` and `pending_commits`, retain its exact pending full hashes (or `none`), verify each commit is reachable from the saved `history_head`, verify that head is an ancestor of the current head, and include the union of pending commits and `history_head..HEAD` without repeats. Missing one field, malformed, duplicate, missing, or branch-mismatched queue is unsafe. A preexisting queue can represent previously selected initial history: do not abandon it. For older state without this pair use its valid `last_commit..HEAD` instead. In merge DAGs the queue, NOT `last_commit..HEAD`, is authoritative for already selected but unprocessed hashes. Order the union by `git rev-list --topo-order --reverse HEAD`, filtering only selected full IDs, and ensure its size matches the deduplicated selection. Once all selected IDs have been represented, retire the legacy queue fields in the final state.

## Bounded, complete collection

- **New recap only:** `bash scripts/collect-git-context.sh "$root"` selects at most the latest 100 unique reachable commits (or all if fewer). It reports the oldest included full hash (`coverage_oldest`) and the selected `HEAD`; write both to `Scope` as the inclusive coverage boundary and explicitly state whether older history exists outside that initial window. Never present earlier history as summarized. Do not start a new recap when an existing recap lacks a safe checkpoint.
- **Existing recap:** after the guards, `bash scripts/collect-git-context.sh "$root" "$checkpoint" 0 "$head"` reports the count and first batch of the COMPLETE checkpoint-to-HEAD range; when migrating an old pending queue collect from `history_head`, then include the verified queued IDs. The helper's `total`, `offset`, `next_offset`, and `has_more` are a continuation contract, NOT a 100-commit invocation limit. Read the next batch using `next_offset` and the same pinned `head`; continue until `has_more: no`, and verify number and uniqueness of all selected IDs. Every batch is at most 100 hashes; for ranges longer than 1,000, keep paging. Never quietly stop after a page, use `last_commit` as a substitute for a pending merge queue, or assert coverage based on a sample. Reconfirm HEAD and branch before final write. If they changed, discard the draft and restart; do not advance old state.
- For EACH selected commit, inspect the Git graph, changes and relevant files. `bash scripts/changed-files.sh "$root" "$commit" [offset] [limit]` lists first-parent name/status changes in pages of at most 100 with an explicit total and continuation offset; retrieve further pages when necessary. Review relevant diffs, tests, configuration, and explicit follow-ups. Group related commits by outcome rather than echoing subjects. Account for every selected full hash exactly once in a dated entry's `Commits` field, including merges and commits with no distinct diff; don't duplicate an older entry's hashes. A title is a lead, not evidence. Mark unverifiable motivation and impact `Unknown` or `Needs verification`.
- Keep staged, unstaged, and untracked changes under `Current Point` as **Uncommitted work**, separate from completed committed entries; distinguish the skill-owned recap file itself. Only claim a test passed when its command/result was actually observed; otherwise say `not run`, `unknown`, or `reported by commit`.

## All-or-nothing publish

1. Build the full candidate in a temporary file, including EVERY selected commit, the unchanged earlier entries, the initial coverage boundary where applicable, and refreshed `Current Point`. Do not modify `docs/recap.md` during analysis or between batches. The final checkpoint (`last_commit`) is `HEAD` only after the entire selected range is represented; for a repeat run with zero commits preserve it and append no entry. A candidate with missing commits is incomplete and MUST be discarded. Use `branch`, full `last_commit`, `last_updated`, and `output_sha256` in the final `recap-state`; obsolete `history_head`/`pending_commits` are removed only after their queued hashes are represented. `Current Point` must show actual HEAD, branch, checkpoint, pending history (`None` only if the checkpoint equals HEAD), committed and uncommitted work separately.
2. Save a temporary file of ALL selected full IDs (one per line, oldest-first); validate the candidate using `bash scripts/validate-recap.sh "$root" "$draft" "$selected_ids" "$head"`. The validator checks structure, ownership hash, state, and the complete selected set; fix the draft if it fails. Compare the original recap's exact hash/bytes and branch/HEAD again immediately before publish to catch concurrent edits; re-run ownership and ancestry guards. If the starting recap or Git state has changed, discard the candidate and restart; never overwrite user changes. On success, atomically rename the validated complete draft to `docs/recap.md` on the same filesystem. Clean temporary files even on interruption. No separate checkpoint file, partial entry, or intermediate publish is allowed.
3. Verify only `docs/recap.md` was intended to change; older entries remain byte-for-byte intact; every selected commit appears exactly once in entries; state and fingerprint match the complete file; no inferred test success appears; initial older-history exclusion is explicit. A failed or interrupted analysis leaves the existing recap and checkpoint unchanged.

Use the template's `Scope`, dated work entries, and `Current Point`. Categories: `features`, `fixes`, `refactors`, `infrastructure`, `testing`, `documentation`, `security`, `performance`. Distinguish observed facts from commit-author claims and inference. The only generated output is `docs/recap.md`.
