# Incremental Project Recap

Maintain an evidence-based, append-only `docs/recap.md`. Use only this skill's `scripts/` and `references/recap-template.md`; it must work when installed alone. Scripts collect and validate facts but never interpret commits, edit the repository, or advance a checkpoint. Only the agent writes the recap. Create `docs/` if needed; never edit another generated document.

## Ownership and history guards

1. Find the Git root, non-empty branch, full `HEAD`, and working-tree status. Stop for a non-Git directory, empty repository, detached HEAD, or shallow history: its boundary cannot be verified. Do not invent a checkpoint. Inspect optional `docs/overview.md` and `docs/backlog.md` only as context, and verify their claims against Git evidence.
   Store the absolute target Git root and full `HEAD` as `$root` and `$head`; store the absolute directory containing this `SKILL.md` as `$skill_dir`. Helpers are under `$skill_dir/scripts/`, and their repository argument is always `$root`. Each terminal call starts a fresh shell, so reassign these variables in every command that uses them or use the absolute helper path directly. Never substitute `$PWD` for `$root`: the current directory may be the skill installation. For example: `bash "$skill_dir/scripts/validate-checkpoint.sh" "$root" "$root/docs/recap.md" "$head"`.
2. Read the entire existing recap before updating. If it has a fingerprint, run `bash "$skill_dir/scripts/validate-checkpoint.sh" "$root" "$root/docs/recap.md" "$head"`. A fingerprint mismatch, malformed or duplicate field, missing checkpoint, or branch change is a stop: preserve all entries and state and report the specific reason. If the checkpoint still exists but is no longer an ancestor after a history rewrite, run `bash "$skill_dir/scripts/validate-checkpoint.sh" "$root" "$root/docs/recap.md" "$head" --recover`. Continue ONLY when it reports exactly one `recovery_boundary` based on a documented common ancestor, a complete old history head, an empty pending queue, and no already represented commits after that boundary in the new graph. If recovery fails, report its reason (missing commit, undemonstrated boundary, divergent merge bases, outstanding queue, or changed ownership), leave the published recap/checkpoint untouched, and ask for human review; never guess continuity. Fingerprint checks apply even if the recap is staged or unstaged. The SHA-256 fingerprint is the lowercase digest of the exact UTF-8 document bytes after deleting ONLY its complete `output_sha256: ...` line and line terminator. Keep all other bytes, delimiters, line endings, and whitespace exactly as they were. Require one correct field immediately before the closing `-->` of the final `recap-state` block. For updates compute it over the completed fingerprint-free draft and insert that line immediately before `-->`.
3. For an existing recap without a fingerprint (legacy), run `bash "$skill_dir/scripts/validate-legacy-recap.sh" "$root" "$root/docs/recap.md" "$head"` **before** drafting. This read-only guard requires a clean tracked `docs/recap.md`, one matching `Current Point` and state checkpoint, the same branch, and reachable history; an unsigned document with queue fields is ambiguous. On any failure stop clearly without modifying the source, even if a replacement draft looks valid. If safe, retain its Scope and old entries byte-for-byte (old entries need not meet today's work-entry format); insert only new entries in the current template's format, replace only Current Point and state, and add the fingerprint, branch, history head, and exact remainder queue on the first complete publication. Also add `legacy_prefix: N HASH` to state: `N` is the count of original dated entries, `HASH` is the SHA-256 of the exact source bytes before `## Current Point`; preserve this field unchanged on subsequent signed updates. Do not adopt legacy work already represented in the old entries or publish an empty duplicate batch. After publication future invocations use signed-checkpoint validation.
4. If prior state has both `history_head` and `pending_commits`, verify the pinned head, queue, reachability, and branch as described above. Combine still-unrepresented queued IDs with commits since that pinned head, order oldest-first, and select at most 100. Keep the remaining IDs in the queue with the current pinned `HEAD`; never lose them when the next recap checkpoint does not contain every older commit in a merge graph. Without a queue or recovery boundary, continue from the safe `last_commit` checkpoint. Recovery requires a completely represented old head (`history_head` equal to the old checkpoint, with `pending_commits: none`); otherwise stop. Never pass a whole pending queue via `awk -v`, `xargs`, or any single command argument: it can exceed OS limits.

## Bounded, complete collection

- **New recap only:** `bash "$skill_dir/scripts/collect-git-context.sh" "$root"` selects the latest 100 unique reachable commits (or all if fewer), oldest-to-newest. In `Scope`, use exactly `- **Committed range:** Initial window: `<coverage_oldest>` through `<captured HEAD>`, inclusive.` with full hashes, then `- **Older history:** Outside initial coverage` if `older_history: yes`, or `- **Older history:** None; all reachable commits covered` if `older_history: no`. This is the inclusive initial coverage boundary; preserve both lines on later appends, never imply older commits were summarized. Do not start a new recap when an existing recap lacks a safe checkpoint.
- **Existing recap:** after the guards, select only the oldest 100 unrepresented commits. After a proved rewrite, use `recovery_boundary` instead of the stale checkpoint to collect the complete `recovery_boundary..HEAD` history; do not replay the orphaned old checkpoint or copy old IDs into the new queue. State in the new entry and `Current Point` that the previously documented work remains historical but is not part of the current graph. Stop unchanged if no new commit follows the recovery boundary. Without recovery, if the source has no validated queue, call `bash "$skill_dir/scripts/collect-git-context.sh" "$root" "$checkpoint" 0 "$head"` once and use its commit records; derive the complete checkpoint-to-`HEAD` history in a temporary file to retain the remainder. If the source has a validated queue, do not derive progress from `last_commit..HEAD`. Write the prior queue to a temporary file, one ID per line, using `awk '/^pending_commits: / {print substr($0,18)}' "$source" | tr ' ' '\n' > "$pending_ids"`; for `none`, use an empty file. Write `git -C "$root" rev-list "$history_head..$head"` to `$new_ids`. Merge membership using `awk 'FILENAME==ARGV[1] || FILENAME==ARGV[2] {want[$0]=1; next} want[$0] {print}' "$pending_ids" "$new_ids" <(git -C "$root" rev-list --topo-order --reverse "$head") > "$eligible_ids"`. This retains queued commits through merges and puts the complete eligible history oldest-first. Take only the first 100 lines into `$selected_ids`; keep the rest in their exact order. Do not page again within the invocation.
- **Continuation state:** Set `history_head` to the invocation's captured `HEAD` on every publication. For an existing recap, `pending_commits` must be the exact unrepresented full IDs left after the batch in oldest-first order; for a new initial-window recap or a caught-up recap, use `none`. Generate the remainder from the eligible file, not from the scalar checkpoint: `awk 'NR>100 {printf "%s%s", separator, $0; separator=" "} END {if (NR<=100) printf "none"; print ""}' "$eligible_ids"` writes the field value without passing it as a process argument. When a legacy source lacks queue fields, derive the complete checkpoint-to-`HEAD` history first, then store only IDs not selected in this batch. A `Current Point` count is not a continuation queue. If there are no eligible commits and the existing recap is already caught up at `HEAD`, leave the published recap unchanged.
- Inspect commit metadata and changed-file summaries for every selected ID, oldest-first. For large batches, save the IDs and collect one inventory in a single pass: `while IFS= read -r id; do git -C "$root" show -s --format='%H%x09%P%x09%ad%x09%s' --date=short "$id"; bash "$skill_dir/scripts/changed-files.sh" "$root" "$id"; done < "$selected_ids"`. Open file contents only as needed to support a concrete outcome; inspect merge parent/diff evidence when relevant. For a repeated numbered-record series, inspect representative first/last files and group the series only when their contents confirm the same pattern; keep every selected ID. Group other related commits only when evidence supports one outcome. If deeper motivation or impact is unverified, state the narrower observed outcome and mark impact `Unknown` or `Needs verification`; do not abandon a bounded batch solely because it contains 100 commits. Put every selected full commit ID exactly once as inline code on its dated entry's single physical `- **Commits:**` field line inside collapsed `<details>`; grouped outcomes repeat each hash-and-note pair there. Include merges and empty commits; do not duplicate IDs in prose or prior entries.
- Keep staged, unstaged, and untracked changes under `Current Point` as **Uncommitted work**, separate from completed committed entries; distinguish the skill-owned recap file itself. Only claim a test passed when its command/result was actually observed; otherwise say `not run`, `unknown`, or `reported by commit`.

## All-or-nothing publish

1. Build one complete candidate for this invocation in a temporary file, including no more than 100 selected commits, unchanged earlier entries, the initial coverage boundary where applicable, and refreshed `Current Point`. Do not modify `docs/recap.md` during analysis. Advance `last_commit` only to the final commit represented by this published batch; if history remains, disclose it and preserve the remaining queue/boundary for the next invocation. A candidate with missing commits is incomplete and MUST be discarded. Use `branch`, full `last_commit`, `last_updated`, and `output_sha256` in the final state. `Current Point` must show actual HEAD, branch, checkpoint, pending history, committed work, and uncommitted work separately.
   For an existing recap, begin with an exact copy of the source. Keep Scope and every prior dated entry byte-for-byte; insert new entries immediately before `Current Point`, then replace only `Current Point` and the recap-state block. Never regenerate prior entries from summaries.

  After collection, continue through drafting and validation; a 100-commit batch is still one bounded invocation, not a reason to stop. For a repeated numbered-record series, use verified chronological groups of at most 10 commits per entry (about 10 entries for 100 commits), rather than one entry per commit or one entry for the entire batch. Inspect representative files within each group, list each selected ID exactly once on that entry's single physical `- **Commits:**` line, and state `Unknown` when evidence does not establish impact. Never wrap IDs onto continuation lines. Stop and discard the candidate if ownership, checkpoint, integrity, concurrent-state, or validation checks fail; unknown impact alone does not block completion.
2. Save a temporary file of selected full IDs (one per line, oldest-first). For an existing recap, snapshot its exact original bytes before drafting; for first creation use `INITIAL`. Validate with `bash "$skill_dir/scripts/validate-recap.sh" "$root" "$draft" "$selected_ids" "$head" "$source"`, ensuring the IDs match the oldest eligible batch of at most 100 and appear exactly once inside collapsed technical details. Check ownership, state, secret safety, and append-only bytes. Compare the original recap's exact bytes and branch/HEAD again immediately before publication; if validation or concurrent-state checks fail, discard the candidate without changing the published recap or checkpoint. On success atomically rename the validated complete draft over `"$root/docs/recap.md"` on the same filesystem.
  A nonzero validator result is a hard stop: do not copy, rename, or otherwise publish the candidate. Repair only the temporary draft and rerun validation; if it still fails, leave the published recap and checkpoint unchanged.
3. Verify only `docs/recap.md` was intended to change; older entries remain byte-for-byte intact; every selected commit appears exactly once in entries; state and fingerprint match the complete file; no inferred test success appears; initial older-history exclusion is explicit. A failed or interrupted analysis leaves the existing recap and checkpoint unchanged.

Use the template's `Scope`, dated work entries, and `Current Point`. Categories: `features`, `fixes`, `refactors`, `infrastructure`, `testing`, `documentation`, `security`, `performance`. Distinguish observed facts from commit-author claims and inference. The only generated output is `docs/recap.md`.
