# Incremental Project Recap

Maintain an evidence-based, append-only `docs/recap.md`. Use only this skill's `scripts/` and `references/recap-template.md`; it must work when installed alone. Scripts collect and validate facts but never interpret commits, edit the repository, or advance a checkpoint. Only the agent writes the recap. Create `docs/` if needed; never edit another generated document.

## Ownership and history guards

1. Find the Git root, non-empty branch, full `HEAD`, and working-tree status. Stop for a non-Git directory, empty repository, detached HEAD, or shallow history: its boundary cannot be verified. Do not invent a checkpoint. Inspect optional `docs/overview.md` and `docs/backlog.md` only as context, and verify their claims against Git evidence.
2. Read the entire existing recap before updating. If it has a fingerprint, run `bash scripts/validate-checkpoint.sh "$root" "$root/docs/recap.md" "$head"`. A mismatch, malformed or duplicate field, missing/rebased/non-ancestor commit, or branch change is a stop: preserve all entries and state and ask for direction; inspect refs/graph when helpful, but never guess continuity. Fingerprint checks apply even if the recap is staged or unstaged. The SHA-256 fingerprint is the lowercase digest of the exact UTF-8 document bytes after deleting ONLY its complete `output_sha256: ...` line and line terminator. Keep all other bytes, delimiters, line endings, and whitespace exactly as they were. Require one correct field immediately before the closing `-->` of the final `recap-state` block. For updates compute it over the completed fingerprint-free draft and insert that line immediately before `-->`.
3. For an existing recap without a fingerprint (legacy), adopt it ONLY if `git ls-files --error-unmatch docs/recap.md` succeeds and `git status --short -- docs/recap.md` is empty. Verify its `Current Point` branch (`HEAD ... on <branch>`) exactly matches the current branch, its last checkpoint is an unambiguous ancestor of `HEAD`, and all existing entries remain intact. Otherwise ask; never silently treat it as a new recap or ignore unowned edits. Add a fingerprint and branch on the first safe complete update.
4. If prior state has both `history_head` and `pending_commits`, verify the pinned head, queue, reachability, and branch as described above. Combine still-unrepresented queued IDs with commits since that pinned head, order oldest-first, and select at most 100. Keep the remaining IDs in the queue with the current pinned `HEAD`; never lose them when the next recap checkpoint does not contain every older commit in a merge graph. Without a queue, continue from the safe `last_commit` checkpoint.

## Bounded, complete collection

- **New recap only:** `bash scripts/collect-git-context.sh "$root"` selects the latest 100 unique reachable commits (or all if fewer), oldest-to-newest. It reports the oldest included full hash (`coverage_oldest`) and selected `HEAD`; write both to `Scope` as the inclusive coverage boundary and state whether older history lies outside the initial window. Never imply older commits were summarized. Do not start a new recap when an existing recap lacks a safe checkpoint.
- **Existing recap:** after the guards, select only the oldest 100 unrepresented commits (or fewer) in history order. Call `bash scripts/collect-git-context.sh "$root" "$checkpoint" 0 "$head"` once for this invocation; its `total` is remaining eligible history, its `has_more` indicates whether another run is needed, and its `commit:` records are the one batch to review. Do not page again within this invocation. For an existing validated pending queue, merge its unrepresented IDs with commits added since its pinned `history_head`, order them by `git rev-list --topo-order --reverse HEAD`, and take only the first 100. Show remaining history in `Current Point`; later invocations resume from the oldest unrepresented commit.
- For EACH selected commit, inspect the Git graph, changes and relevant files. `bash scripts/changed-files.sh "$root" "$commit" [offset] [limit]` gives an aggregate change summary and first-parent name/status changes in pages of at most 100; retrieve pages as needed for that commit. Group related commits by outcome. Lead with a short, plain-language outcome and impact. Put exactly one full commit ID per selected commit plus supporting technical notes inside a collapsed `<details>` block; never duplicate IDs in prose or prior entries. Account for every selected full hash exactly once, including merges and empty commits. A title is a lead, not evidence; mark unverifiable motivation or impact `Unknown` or `Needs verification`.
- Keep staged, unstaged, and untracked changes under `Current Point` as **Uncommitted work**, separate from completed committed entries; distinguish the skill-owned recap file itself. Only claim a test passed when its command/result was actually observed; otherwise say `not run`, `unknown`, or `reported by commit`.

## All-or-nothing publish

1. Build one complete candidate for this invocation in a temporary file, including no more than 100 selected commits, unchanged earlier entries, the initial coverage boundary where applicable, and refreshed `Current Point`. Do not modify `docs/recap.md` during analysis. Advance `last_commit` only to the final commit represented by this published batch; if history remains, disclose it and preserve the remaining queue/boundary for the next invocation. A candidate with missing commits is incomplete and MUST be discarded. Use `branch`, full `last_commit`, `last_updated`, and `output_sha256` in the final state. `Current Point` must show actual HEAD, branch, checkpoint, pending history, committed work, and uncommitted work separately.
2. Save a temporary file of selected full IDs (one per line, oldest-first). For an existing recap, snapshot its exact original bytes before drafting; for first creation use `INITIAL`. Validate with `bash scripts/validate-recap.sh "$root" "$draft" "$selected_ids" "$head" "$source"`, ensuring the IDs match the oldest eligible batch of at most 100 and appear exactly once inside collapsed technical details. Check ownership, state, secret safety, and append-only bytes. Compare the original recap's exact bytes and branch/HEAD again immediately before publication; if validation or concurrent-state checks fail, discard the candidate without changing the published recap or checkpoint. On success atomically rename the validated complete draft over `docs/recap.md` on the same filesystem.
3. Verify only `docs/recap.md` was intended to change; older entries remain byte-for-byte intact; every selected commit appears exactly once in entries; state and fingerprint match the complete file; no inferred test success appears; initial older-history exclusion is explicit. A failed or interrupted analysis leaves the existing recap and checkpoint unchanged.

Use the template's `Scope`, dated work entries, and `Current Point`. Categories: `features`, `fixes`, `refactors`, `infrastructure`, `testing`, `documentation`, `security`, `performance`. Distinguish observed facts from commit-author claims and inference. The only generated output is `docs/recap.md`.
