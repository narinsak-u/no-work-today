# Incremental Project Recap

Maintain one evidence-based, append-only project memory at `docs/recap.md`. Summarize completed repository work without rereading or rewriting history that a prior checkpoint already covers, and keep current uncommitted work visibly separate from committed work.

## Boundaries

- The only generated output is `docs/recap.md`; create `docs/` when it does not exist.
- Read `references/recap-template.md` from this skill before creating or updating the recap. Use its headings and exact checkpoint shape; do not depend on another skill or an external template.
- Preserve every existing dated work entry. Append entries only for commits represented in the current history batch; record the initial selected window in `Scope` once.
- After initialization, update only newly appended entries, the mutable `Current Point` section, and the final `recap-state` comment.
- Never present staged, unstaged, or untracked work as completed history. Never stage, commit, reset, discard, or amend repository work while producing the recap.
- Use repository evidence. Distinguish observed facts from commit-author claims and inferences. Mark unsupported or unavailable information as `Unknown`, `Needs verification`, `not run`, or `reported by commit` rather than guessing.

## Incremental workflow

1. **Establish the repository state.** Confirm the repository root, current non-empty branch name, current `HEAD`, and working-tree status. Stop and ask if the repository is in detached-HEAD state or has no commit. Inspect the existing `docs/` directory without assuming it exists. Check for `docs/overview.md` and `docs/backlog.md` as optional context; verify their claims against Git evidence and do not edit them.
2. **Read and guard the existing recap.** If `docs/recap.md` exists, read all prior entries and its final HTML `recap-state` comment. New state stores `branch`, `history_head`, `pending_commits`, `last_commit`, `last_updated`, and `output_sha256`. Encode `pending_commits` as `none` when empty, otherwise as every unprocessed full commit hash separated by single spaces in oldest-to-newest topological order; do not use ranges or abbreviations. If exactly one of `history_head` and `pending_commits` is missing, or the queue is malformed, stop and ask rather than guessing. Validate `output_sha256` before any write:
   - The fingerprint is the lowercase SHA-256 hex digest of the exact UTF-8 bytes of the whole document after removing only the complete `output_sha256: <value>` line, including that line's line terminator. Keep the comment delimiters, every other metadata field, all other bytes, and the surrounding line breaks in the hashed content. Do not normalize line endings, whitespace, encoding, or trailing newlines. Require exactly one well-formed fingerprint field; malformed, duplicate, or non-matching fields are invalid.
   - After every permitted update, form the complete document with the `output_sha256` line omitted, hash those exact bytes, and insert `output_sha256: <64 lowercase hex characters>` immediately before the closing `-->` of `recap-state`. On a new recap, create the state comment and fingerprint together. Keep this metadata in `docs/recap.md`; do not create another output.
   - A matching fingerprint proves that the document's current content is still skill-owned, so it may be updated even if Git reports `docs/recap.md` as staged or unstaged. A present but invalid fingerprint means user edits or corruption: stop, ask how to preserve or merge them, and do not write anything.
   - If the fingerprint is absent, treat the recap as legacy. Adopt it only if `git ls-files --error-unmatch docs/recap.md` succeeds and `git status --short -- docs/recap.md` is empty. An untracked, modified, staged, or non-Git legacy recap cannot be proven safe; stop and ask. Never infer that a missing fingerprint is valid.
3. **Bind the recap to one branch.** For a state comment with `branch`, compare it exactly with the current branch before inspecting or changing history; on mismatch, stop for user direction without writing or changing the baseline. For a legacy checkpoint with no `branch`, read the branch recorded in its `Current Point` `HEAD` line (`... on <branch>`); adopt only if that branch is present, unambiguous, and exactly matches the current branch. Otherwise stop and ask. Write the current branch into new and upgraded state comments.
4. **Choose a safe history boundary.**
   - Only when `docs/recap.md` does not exist, initialize a history window: use `git rev-list --topo-order --reverse --max-count=1000 HEAD` to select at most the latest 1,000 unique commits reachable from the current branch, in oldest-to-newest topological order. Compare with `git rev-list --count HEAD` to determine whether older history was omitted. Record the selected range (oldest selected commit through the initial `HEAD`, inclusive) in `Scope`. If more than 1,000 commits exist, explicitly state that older history is outside this recap's initial coverage; never imply it was summarized. Put the selected full commit hashes, in that order, into the initial `pending_commits` queue before processing a batch.
   - In new-format state, require `history_head` to resolve unambiguously and be an ancestor of current `HEAD`. Validate that every queued commit resolves and is reachable from `history_head`. Find newly reachable commits only in `history_head..HEAD`. Merge those hashes with the existing queue, deduplicate by full hash, and keep the combined queue in current `HEAD`'s oldest-to-newest topological order. `history_head` is the branch tip whose reachable additions have been reconciled into the queue; it is not the recap checkpoint.
   - Never use `last_commit..HEAD` as the new-format resume cursor. In a merge DAG, a scalar commit can be one topological position without being an ancestor-prefix of all already processed commits; that range can repeat summarized side-parent commits. The explicit pending queue is the exact unprocessed set. `last_commit` remains the final commit represented by the latest completed batch.
   - For an older state without `history_head` and `pending_commits`, require its `last_commit` to resolve and be an ancestor of current `HEAD`. Seed the queue with commits in `last_commit..HEAD`, ordered oldest-to-newest, then persist the current `HEAD` as `history_head` with that queue. This migration is allowed only after fingerprint/legacy and branch guards pass. An existing recap with no unambiguous checkpoint is not a new recap; surface uncertainty and ask rather than restarting its history.
   - For merges, inspect the graph and relevant diffs rather than treating every parent or merge commit as a separate feature. If the saved `history_head` (or a legacy `last_commit`) is missing, ambiguous, or no longer an ancestor because of a rebase, force-push, or rewritten boundary, inspect available refs and graph context. Never infer ancestry from similar subjects or silently reread all history. If a continuous boundary cannot be verified, preserve old entries and cursor state, surface the discontinuity as `Needs verification`, and ask for direction; do not advance to an unverified `HEAD`.
5. **Bound each history batch.** Enumerate or count pending IDs as needed for `Current Point`, but analyze commit evidence and summarize no more than 100 commits per invocation. Order the exact candidate set (prior `pending_commits` plus newly reachable hashes) oldest-to-newest topologically using current `HEAD`'s Git order, then process only its first 100 IDs. Do not inspect diffs for other commits. Remove from the queue only the hashes fully represented by this batch. After all new reachable hashes have been added to the queue, set `history_head` to the pinned starting `HEAD`. If that `HEAD` changes before writing, stop and rerun against the new state.
6. **Inspect only the batch evidence.** For each selected commit, inspect the narrowest relevant Git diff, changed files, tests, configuration, and explicit follow-ups needed to explain behavior. Group related commits that implement one coherent change; do not make one recap item per commit. Account for every selected commit in grouped entries, including merges or commits with no distinct change; list each selected full hash exactly once in the corresponding `Commits` field. Do not duplicate hashes already present in earlier entries.
7. **Separate committed and uncommitted work.** Build dated entries only from the verified batch. Inspect staged, unstaged, and untracked changes separately and list them under `Current Point` as `Uncommitted work`, with their status and verification limits. Keep the skill-owned recap output distinguishable from project work. If a worktree change is relevant to a committed entry, state the distinction explicitly; do not fold it into completed impact.
8. **Write from the local template.** Include the template's `Scope`, dated work entries, categories, status, what/why, important files, commits, impact, junior notes, verification, and `Current Point`. For each entry, choose one of the template categories: `features`, `fixes`, `refactors`, `infrastructure`, `testing`, `documentation`, `security`, or `performance`. Explain impact only when supported by the diff or explicit repository context. Record exact observed verification commands and outcomes; use `not run`, `unknown`, or `reported by commit` when no result was observed.
9. **Checkpoint only represented commits.** Append new dated grouped entries immediately before `Current Point`, set `last_commit` to the final commit fully represented by this batch—not automatically to `HEAD`—and update `last_updated`.
   Persist the remaining exact `pending_commits` queue and reconciled `history_head` in `recap-state`, then recalculate the fingerprint.
   In `Current Point`, report actual `HEAD` and branch, recap checkpoint, and pending history separately; show the pending count and next up-to-100 oldest-first hashes. Never claim to be caught up while the queue is non-empty; say `None` only when the queue is empty and the checkpoint equals `HEAD`.
   If the queue is empty, `history_head` equals `HEAD`, and `last_commit` equals `HEAD`, add no historical entry and preserve `last_commit`; refresh only mutable current-state details when needed.
10. **Re-read and audit the result.** Confirm old entries remain intact, every new entry maps to one batch hash, no hash occurs twice, the checkpoint is the final represented commit, the pending queue contains every unprocessed selected/new commit exactly once, the initial 1,000-commit limit and any older-history omission are visible, committed and uncommitted work are distinct, no test result is invented, `Current Point` reflects actual `HEAD`/branch/queue, and the fingerprint validates. Confirm only `docs/recap.md` (and possibly `docs/`) was intended to change.

## Evidence rules

- A commit title is a lead, not proof of behavior. Inspect the relevant diff before stating what changed or why.
- A test file, script, or CI configuration does not prove a check passed. Claim `verified` only for a command or CI result actually observed in the scoped work; otherwise say `not run`, `unknown`, or `reported by commit`.
- Do not infer motivation, user impact, performance, coverage, release state, or roadmap items from filenames, commit counts, or conventional project patterns.
- If history was rewritten, the branch changed, or a checkpoint cannot be resolved, preserve continuity and make the boundary uncertainty visible instead of manufacturing a complete timeline.

## Completion criteria

A recap update is complete when `docs/recap.md` uses the local template, preserves all earlier entries, adds grouped evidence-backed entries only for the verified history batch, reports actual `HEAD`, branch, recap checkpoint, and pending history in `Current Point`, records a valid fingerprint whose `last_commit` is the latest commit fully represented, makes any older-history omission visible, and labels uncommitted or unverified information explicitly. No unrelated file is modified.
