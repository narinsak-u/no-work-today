# Incremental Project Recap

Maintain an evidence-based, append-only `docs/recap.md`. Use only this skill's `scripts/` and `references/recap-template.md`; it must work when installed alone. Scripts collect and validate facts but never interpret commits, edit the repository, or advance a checkpoint. Only the agent writes the recap. Create `docs/` if needed; never edit another generated document.

## Ownership and history guards

1. Find the Git root, branch, and working-tree status. Stop for a non-Git directory, detached HEAD, shallow history, or an unborn branch when commits already exist on other refs: those histories cannot be treated as an empty repository. Run `bash "$skill_dir/scripts/collect-git-context.sh" "$root"` to distinguish a genuine empty Git repository (`mode: empty`, `head: none`, `total: 0`) from a committed branch. Never invent a commit or checkpoint. Inspect optional `docs/overview.md` and `docs/backlog.md` only as context, and verify their claims against Git evidence.
   Store the absolute target Git root as `$root`, the reported `head` as `$head` (`none` only for a genuine empty repository), and the absolute directory containing this `SKILL.md` as `$skill_dir`. Helpers are under `$skill_dir/scripts/`, and their repository argument is always `$root`. Each terminal call starts a fresh shell, so reassign these variables in every command that uses them or use the absolute helper path directly. Never substitute `$PWD` for `$root`: the current directory may be the skill installation. For example: `bash "$skill_dir/scripts/validate-checkpoint.sh" "$root" "$root/docs/recap.md" "$head"`.
2. Read the entire existing recap before updating. If it has a fingerprint, run `bash "$skill_dir/scripts/validate-checkpoint.sh" "$root" "$root/docs/recap.md" "$head"`. A mismatch, malformed or duplicate field, missing/rebased/non-ancestor commit, or branch change is a stop: preserve all entries and state and ask for direction; inspect refs/graph when helpful, but never guess continuity. Fingerprint checks apply even if the recap is staged or unstaged. The SHA-256 fingerprint is the lowercase digest of the exact UTF-8 document bytes after deleting ONLY its complete `output_sha256: ...` line and line terminator. Keep all other bytes, delimiters, line endings, and whitespace exactly as they were. Require one correct field immediately before the closing `-->` of the final `recap-state` block. For updates compute it over the completed fingerprint-free draft and insert that line immediately before `-->`.
3. For an existing recap without a fingerprint (legacy), adopt it ONLY if `git -C "$root" ls-files --error-unmatch docs/recap.md` succeeds and `git -C "$root" status --short -- docs/recap.md` is empty. Verify its `Current Point` branch (`HEAD ... on <branch>`) exactly matches the current branch, its last checkpoint is an unambiguous ancestor of `HEAD`, and all existing entries remain intact. Otherwise ask; never silently treat it as a new recap or ignore unowned edits. Add a fingerprint and branch on the first safe complete update.
   In an empty repository, an existing recap must have a valid fingerprint and the explicit empty state described below; never adopt an unsigned or untracked legacy recap as history. If the first commit appears after an empty recap was published, stop rather than treat `none` as an ancestor or silently overwrite the prior document; a new committed-history boundary requires separate safe handling.
4. If prior state has both `history_head` and `pending_commits`, verify the pinned head, queue, reachability, and branch as described above. Combine still-unrepresented queued IDs with commits since that pinned head, order oldest-first, and select at most 100. Keep the remaining IDs in the queue with the current pinned `HEAD`; never lose them when the next recap checkpoint does not contain every older commit in a merge graph. Without a queue, continue from the safe `last_commit` checkpoint.

## Bounded, complete collection
- **No commits:** If collection reports `mode: empty`, do not inspect commit history, create dated work entries, or claim completed work. Record `No commits yet; this Git repository has no committed history.` as the Scope's committed range. In `Current Point`, use `No commits yet on \`<branch>\`` for HEAD, `None (no commits yet)` for the recap checkpoint, `None` for pending committed history, and `None; no commits exist.` for committed work. Describe real staged, unstaged, and untracked files as uncommitted work and give a safe next step. State `last_commit: none`, `history_head: none`, and `pending_commits: none`, with the real branch, date, and fingerprint. An existing signed empty recap may be refreshed without changing its Scope. Treat `none` as an explicit no-commit state, never a placeholder commit ID.
- **New committed recap only:** `bash "$skill_dir/scripts/collect-git-context.sh" "$root"` selects the latest 100 unique reachable commits (or all if fewer), oldest-to-newest. It reports the oldest included full hash (`coverage_oldest`) and selected `HEAD`; write both to `Scope` as the inclusive coverage boundary and state whether older history lies outside the initial window. Never imply older commits were summarized. Do not start a new recap when an existing recap lacks a safe checkpoint.
- **Existing recap:** after the guards, select only the oldest 100 unrepresented commits. If the source has no validated queue, call `bash "$skill_dir/scripts/collect-git-context.sh" "$root" "$checkpoint" 0 "$head"` once and use its commit records. If it has a validated queue, do not derive progress from `last_commit..HEAD`; merge pending IDs with commits added since pinned `history_head`, order by `git -C "$root" rev-list --topo-order --reverse "$head"`, and take the first 100. Do not page again within an invocation; later runs resume from the exact queue.
- **Continuation state:** Set `history_head` to the invocation's captured `HEAD` on every publication. For an existing recap, `pending_commits` must be the exact unrepresented full IDs left after the batch in oldest-first order; for a new initial-window recap or a caught-up recap, use `none`. When a legacy source lacks queue fields, derive the complete checkpoint-to-`HEAD` history first, then store only IDs not selected in this batch. A `Current Point` count is not a continuation queue.
- Inspect commit metadata and changed-file summaries for every selected ID, oldest-first. For large batches, save the IDs and collect one inventory in a single pass: `while IFS= read -r id; do git -C "$root" show -s --format='%H%x09%P%x09%ad%x09%s' --date=short "$id"; bash "$skill_dir/scripts/changed-files.sh" "$root" "$id"; done < "$selected_ids"`. Open file contents only as needed to support a concrete outcome; inspect merge parent/diff evidence when relevant. For a repeated numbered-record series, inspect representative first/last files and group the series only when their contents confirm the same pattern; keep every selected ID. Group other related commits only when evidence supports one outcome. If deeper motivation or impact is unverified, state the narrower observed outcome and mark impact `Unknown` or `Needs verification`; do not abandon a bounded batch solely because it contains 100 commits. Put every selected full commit ID exactly once as inline code on its dated entry's single physical `- **Commits:**` field line inside collapsed `<details>`; grouped outcomes repeat each hash-and-note pair there. Include merges and empty commits; do not duplicate IDs in prose or prior entries.
- Keep staged, unstaged, and untracked changes under `Current Point` as **Uncommitted work**, separate from completed committed entries; distinguish the skill-owned recap file itself. Only claim a test passed when its command/result was actually observed; otherwise say `not run`, `unknown`, or `reported by commit`.

## All-or-nothing publish

1. Build one complete candidate for this invocation in a temporary file, including no more than 100 selected commits, unchanged earlier entries, the initial coverage boundary where applicable, and refreshed `Current Point`. Do not modify `docs/recap.md` during analysis. Advance `last_commit` only to the final commit represented by this published batch; if history remains, disclose it and preserve the remaining queue/boundary for the next invocation. A candidate with missing commits is incomplete and MUST be discarded. Use `branch`, full `last_commit` (or `none` only in an empty repository), `last_updated`, and `output_sha256` in the final state. `Current Point` must show actual HEAD, branch, checkpoint, pending history, committed work, and uncommitted work separately.
   For an existing recap, begin with an exact copy of the source. Keep Scope and every prior dated entry byte-for-byte; insert new entries immediately before `Current Point`, then replace only `Current Point` and the recap-state block. Never regenerate prior entries from summaries.
   For empty history, draft from the empty template variant (no dated entries); use a zero-byte selected-IDs file, `$head=none`, and `INITIAL` for first publication (or the prior signed recap for an empty refresh). The same integrity, branch/HEAD recheck, atomic publication, and no-unrelated-writes rules apply. On a changed HEAD or unsafe previous state, discard the draft without publishing.

  After collection, continue through drafting and validation; a 100-commit batch is still one bounded invocation, not a reason to stop. For a repeated numbered-record series, use verified chronological groups of at most 10 commits per entry (about 10 entries for 100 commits), rather than one entry per commit or one entry for the entire batch. Inspect representative files within each group, list each selected ID exactly once on that entry's single physical `- **Commits:**` line, and state `Unknown` when evidence does not establish impact. Never wrap IDs onto continuation lines. Stop and discard the candidate if ownership, checkpoint, integrity, concurrent-state, or validation checks fail; unknown impact alone does not block completion.
2. Save a temporary file of selected full IDs (one per line, oldest-first; zero bytes for empty history). For an existing recap, snapshot its exact original bytes before drafting; for first creation use `INITIAL`. Validate with `bash "$skill_dir/scripts/validate-recap.sh" "$root" "$draft" "$selected_ids" "$head" "$source"`, ensuring selected IDs match the oldest eligible batch of at most 100 (or none in an empty repository). Check ownership, state, secret safety, and append-only bytes. Compare the original recap's exact bytes and branch/HEAD again immediately before publication; if validation or concurrent-state checks fail, discard the candidate without changing the published recap or checkpoint. On success atomically rename the validated complete draft over `"$root/docs/recap.md"` on the same filesystem.
  A nonzero validator result is a hard stop: do not copy, rename, or otherwise publish the candidate. Repair only the temporary draft and rerun validation; if it still fails, leave the published recap and checkpoint unchanged.
3. Verify only `docs/recap.md` was intended to change; older entries remain byte-for-byte intact; every selected commit appears exactly once in entries; state and fingerprint match the complete file; no inferred test success appears; initial older-history exclusion is explicit. A failed or interrupted analysis leaves the existing recap and checkpoint unchanged.

Use the template's `Scope`, dated work entries, and `Current Point`. Categories: `features`, `fixes`, `refactors`, `infrastructure`, `testing`, `documentation`, `security`, `performance`. Distinguish observed facts from commit-author claims and inference. The only generated output is `docs/recap.md`.
