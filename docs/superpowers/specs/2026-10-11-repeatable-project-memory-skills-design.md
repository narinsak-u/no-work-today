## Problem Statement

The project-memory skills are difficult to use repeatedly. Each skill refuses to update its owned document whenever Git reports staged or unstaged changes, including an unchanged document generated by the skill during an earlier, still-uncommitted run. This makes ordinary second invocations stop unnecessarily, while simply removing the guard could overwrite developer edits.

The recap skill also assumes it can inspect the whole pending commit range in one invocation. A repository with a long history can exceed practical context limits, and there is no resumable progress model for processing that history safely across calls.

## Solution

Make all three skills safely repeatable by recording a hidden integrity fingerprint in each skill-owned Markdown document. A repeat invocation may update a document when its fingerprint still matches the content. A missing or invalid fingerprint is never treated as proof that user changes are safe to overwrite: the skill adopts only a clean, tracked legacy document and otherwise stops for user direction.

Make recap history processing incremental and bounded. A first recap covers at most the latest 1,000 commits reachable from the current branch, and each invocation processes at most 100 commits oldest-to-newest. Persist the current branch and the last fully summarized commit. Later calls resume after that recap checkpoint; pending work remains explicit until the checkpoint reaches `HEAD`. Track one branch per recap and ask before switching histories.

## User Stories

1. As a developer, I want to run any project-memory skill more than once without committing its generated document between calls, so that I can use the skills naturally during ongoing work.
2. As a developer, I want a repeat invocation to recognize an unchanged document previously generated by the skill, so that Git’s dirty-file status alone does not block a safe update.
3. As a developer, I want the skill to detect edits made to its generated document after the prior run, so that my work is not silently overwritten.
4. As a developer, I want a missing or invalid document fingerprint to stop the update unless the legacy file is clean and tracked, so that uncertain ownership is resolved conservatively.
5. As a developer, I want clean, tracked legacy overview, recap, and backlog documents adopted safely, so that adding fingerprint support does not require rebuilding committed project memory from scratch.
6. As a developer, I want untracked or modified legacy documents without a fingerprint to require my direction, so that an in-progress document is preserved.
7. As a developer, I want a first recap to cover a bounded recent history window, so that onboarding a large repository does not require analyzing every historical commit.
8. As a developer, I want the first recap to select no more than the latest 1,000 commits reachable from the current branch, so that older history is not silently implied to have been reviewed.
9. As a developer, I want commits in a recap history batch processed oldest-to-newest, so that the checkpoint advances in a deterministic, gap-free order.
10. As a developer, I want each recap invocation to process no more than 100 commits, so that large histories can be handled within bounded work per call.
11. As a developer, I want a later invocation to resume after the last fully summarized commit, so that large initial histories and later accumulated work can be completed incrementally.
12. As a developer, I want the recap to identify its current branch and stop when invoked on another branch, so that unrelated branch histories are not mixed silently.
13. As a developer, I want a legacy recap checkpoint without branch metadata adopted only when its existing `Current Point` branch matches the current branch, so that older recaps can migrate without guessing.
14. As a developer, I want the recap to distinguish current `HEAD` from the recap checkpoint, so that pending commits are visible and the recap never claims to be caught up early.
15. As a developer, I want a recap run with no new commits to avoid adding duplicate history entries, so that repeated calls remain idempotent.
16. As a developer, I want a no-new-commits run to refresh mutable current-state information while preserving the historical entries and last summarized commit, so that uncommitted work remains visible without being misrepresented as completed history.
17. As a developer, I want the recap to state when commits older than the initial 1,000-commit window were omitted, so that its historical coverage is clear.
18. As a developer, I want fingerprint metadata to remain within each owned Markdown document, so that each skill continues to own only its existing output file.

## Implementation Decisions

- Update the existing `to-catchup`, `to-recap`, and `to-backlog` workflows. Preserve their current output ownership, evidence rules, templates, and unrelated-file protections.
- Add a hidden HTML metadata comment to each skill-owned Markdown document containing a SHA-256 fingerprint. Define the fingerprint over the document content with the fingerprint field excluded, so validation does not depend on a self-referential hash.
- Before writing an existing output:
  - If its fingerprint validates, allow the skill to update it even when Git reports the file as dirty.
  - If a fingerprint is present but does not validate, stop and ask how to preserve or merge the edits.
  - If the fingerprint is absent, adopt the document only when it is clean and tracked in Git. Stop for an untracked or modified document. In a non-Git repository, an existing unmarked document cannot be proven clean and requires user direction.
- On a new output, write the document and its fingerprint together. Recalculate the fingerprint after every permitted update.
- Extend recap machine-readable state with the current branch and retain `last_commit` as the last commit whose changes are represented in the recap. Keep the fingerprint metadata in that same state comment.
- For a first recap, select at most the latest 1,000 unique commits reachable from the current branch. Record the selected range and state that older history is outside the recap’s initial coverage.
- Process at most 100 commits per recap invocation, oldest-to-newest. Save progress only through commits represented in the recap. Subsequent invocations continue from the saved checkpoint; commits beyond it remain pending.
- Report actual `HEAD`, branch, last summarized commit, and pending history separately in `Current Point`. Do not claim the recap is caught up while the checkpoint trails `HEAD`.
- When the checkpoint equals `HEAD`, add no historical entry. Preserve the historical entries and `last_commit`; refresh only mutable current-state details when needed.
- A branch mismatch stops for user direction before any history update or baseline change. For a legacy recap checkpoint without branch metadata, use the branch in `Current Point` only when it matches the current branch; otherwise stop and ask.
- Preserve existing behavior for unresolved or rewritten commit boundaries: do not infer ancestry from similar commit subjects, do not silently reread all history, and surface uncertainty rather than inventing continuity.
- Preserve all existing output-specific invariants: overview evidence and secret-handling rules; recap separation of committed and uncommitted work; backlog stable IDs, allowed statuses/priorities, completion records, and item-section consistency.

## Testing Decisions

- Test the skills at the highest useful seam: invoke each skill against isolated temporary project fixtures and observe the resulting owned document and repository state. Tests should assert external behavior, not prompt wording or the presence of implementation instructions.
- For each skill, cover a first write, a second call with a valid unchanged fingerprint while the output is uncommitted, and a user edit that invalidates the fingerprint and must remain untouched while the skill stops.
- Cover legacy migration: clean tracked files without fingerprints can be adopted; untracked or modified files cannot be overwritten; a non-Git repository with an existing unmarked output asks before adoption.
- For recap, use a temporary Git repository with more than 1,000 commits. Verify the first run scopes only the latest 1,000, processes at most 100 oldest-first, and records a checkpoint that matches the summarized range. Verify subsequent calls progress without gaps or duplicate entries until caught up.
- For recap, cover no-new-commit repeat runs, pending history, branch mismatch, legacy branch inference, a branch mismatch with ambiguous legacy metadata, and rewritten/non-ancestor checkpoints.
- For catchup and backlog, verify a valid fingerprint allows safe repeat updates and invalid/missing fingerprints preserve user edits. Retain backlog tests for stable IDs, preserved completed items, status-to-section consistency, and no unsupported work promotion; retain catchup checks for evidence-backed documentation and secret redaction.
- The repository currently has no automated test files or architecture decision records. Existing examples provide representative output shapes, but are not behavioral tests. Add focused skill-level fixture tests rather than tests that merely assert prompt text or copy sample files.

## Out of Scope

- Automatically committing, staging, amending, resetting, or discarding repository changes.
- Tracking multiple branches in one recap or silently switching/re-baselining after a branch change.
- Summarizing all history older than the initial 1,000-commit window during first-run initialization.
- Automatically merging a fingerprint-mismatched document or attempting to infer which changed lines belong to the user versus the skill.
- Changing the overview, recap, or backlog domain content beyond the metadata and recap progress needed for safe repeat runs.
- Changing the backlog ID, status, priority, completion, or section invariants.

## Further Notes

- The project glossary defines a **recap checkpoint** as the latest commit fully represented in `docs/recap.md`, and a **history batch** as up to 100 consecutive commits processed oldest-to-newest in one invocation.
- The selected test seam is a black-box skill invocation in a disposable project fixture; the repository does not currently provide a skill test harness.
- No ADR files were found in the repository.
- GitHub Issues are enabled for the repository, but its current labels do not include `ready-for-agent`, and no triage vocabulary or tracker setup was supplied. Per the `to-spec` workflow, publication and labeling are blocked until the user runs `/setup-matt-pocock-skills`.
